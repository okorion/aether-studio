# 첫 스크롤의 2.8초 멈춤을 추적했다

처음 아래로 내려갈 때 리액터 앞에서 화면이 멈췄다. 다시 올라오면 부드러웠다. 정지한 장면에서 프레임 간격을 재면 약 16.7ms였지만, 첫 하강에는 약 2.8초가 비는 구간이 있었다.

숨겨 둔 장면의 셰이더를 미리 준비하면서 큰 멈춤은 줄었다. 그 뒤 첫 모니터에 남은 지연을 영상 경로별로 비교했고, 마지막에는 경계 뒤에서 계속 실행하던 굴절·반사 패스를 줄였다. 각각 따로 측정한 작업이다.

## p95에서 보이지 않던 멈춤

로컬 production 빌드에서 장면 준비 후 1초를 기다렸다. RAF마다 스크롤 위치를 바꾸며 19초 동안 0→99%를 내려갔고, 800ms 뒤 같은 페이지에서 19초 동안 올라왔다. 환경은 Chromium/ANGLE D3D11, 1440×900, DPR 1이었다.

| 수정 전 | 첫 하강 | 같은 페이지의 상승 |
| --- | ---: | ---: |
| RAF 간격 중앙값 | 16.7ms | 16.7ms |
| RAF 간격 p95 | 16.7ms | 16.7ms |
| 최장 RAF 간격 | 2799.9ms | 16.8ms |
| 33.5ms 초과 | 8회 | 0회 |
| 전환 중 셰이더 컴파일 / 링크 | 66 / 33회 | 0 / 0회 |

긴 멈춤은 표본의 5%보다 적었다. 그래서 p95가 평소 프레임 간격과 같았다. 최댓값과 긴 프레임의 위치를 함께 보니 첫 리액터 진입을 찾아낼 수 있었다.

![첫 진입의 GPU·영상 준비](../images/cold-warm.png)

*개념도. 같은 페이지에서 해당 경로를 처음 쓰는 시점을 뜻한다. OS·드라이버 캐시까지 비운 실험은 아니다.*

## 숨긴 광원이 늘린 셰이더

리액터의 광원이 숨긴 그룹 아래에 있었다. 그룹이 나타나면 렌더러가 보는 광원 수가 바뀌고, 여러 머테리얼이 새 셰이더 프로그램을 준비했다.

광원은 장면에 계속 두고 강도만 바꿨다. 이어서 숨긴 장면도 초기 준비에 포함했다. canvas 출력과 bloom·굴절용 linear half-float 타깃은 서로 다른 프로그램 변형을 쓸 수 있어 양쪽을 준비했다.

`compileAsync()`가 끝난 뒤에도 첫 uniform 조회와 geometry 업로드는 남았다. 2×2 타깃에 실제로 한 번 그려 이 작업까지 실행했다. 정적 텍스처에는 `initTexture()`, 굴절·반사 타깃에는 `initRenderTarget()`을 호출했다. `VideoTexture`는 제외해 지연 로드를 유지했다.

```text
CSS 대체 화면 표시
  → 정적 텍스처 업로드
  → linear 타깃 경로 compileAsync
  → 2×2 타깃에 숨은 geometry 첫 렌더
  → canvas 출력 경로 compileAsync
  → 준비 완료 후 장면 표시
```

준비 중 바꾼 visibility, frustum culling, 반사 콜백, render target은 `finally`에서 돌려놓았다. 화면 해제나 컨텍스트 손실 뒤에 이전 준비 작업이 끝날 수도 있어, 세대 번호와 취소 상태를 확인한 뒤 렌더를 시작했다. 취소·컴파일 실패·첫 렌더 실패 때의 복원은 renderer 모의 테스트로 검사했다.

## 리액터 다음에 남은 모니터 지연

같은 조건으로 다시 내려갔다.

| 최초 하강 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 최장 RAF 간격 | 2799.9ms | 66.6ms |
| 33.5ms 초과 | 8회 | 1회 |
| 전환 중 컴파일 / 링크 | 66 / 33회 | 0 / 0회 |
| 최소 품질 계수 | 0.85 | 1.00 |

리액터와 하단 포레스트 구간은 최대 16.8ms였다. 남은 66.6ms는 첫 모니터 진입에서 나왔다. 표의 최댓값이 서로 다른 위치에서 발생한 셈이다.

초기 준비에 걸린 시간도 따로 남겼다. 수정 후 `ready`는 탐색 시작으로부터 3675.9ms였다. 수정 전에는 동등한 시각을 재지 않아 로딩 시간의 증감은 비교할 수 없었다.

이후 공유 조명 영상을 넣자 첫 모니터에서 약 83ms가 기록됐다. 검은 대체 텍스처로 영상 샘플링 분기를 미리 준비해도 남았다. 이때는 컴파일과 longtask가 잡히지 않아 영상 요청부터 조건을 나눴다.

## 영상 요청을 막자 사라진 긴 프레임

RTX 2060 SUPER, Chromium/ANGLE D3D11, 1440×900, DPR 1에서 첫 모니터 진입만 측정했다. HTTP 캐시를 끈 새 브라우저에서 준비 후 1초를 기다리고, 7초 동안 0→36.5%를 내려갔다. 조건별로 두 번씩, GPU 브라우저는 하나씩 실행했다. lint가 겹친 실행은 대표값에서 제외했다.

| 진단 조건 | 최대 RAF 간격 1회 / 2회 |
| --- | ---: |
| 기존 H.264 모니터 두 편 | 99.9 / 83.3ms |
| 모니터 영상 요청 차단 | 16.8 / 16.8ms |
| 조명 영상 요청만 차단 | 66.7 / 49.9ms |
| 모니터 첫 데이터 수신 후 일시정지 | 83.4 / 66.7ms |
| 모니터 한 편만 허용 | 50.0 / 50.0ms |
| 같은 내용의 VP9 응답 | 50.0 / 116.7ms |
| 같은 내용의 VP8 응답 | 16.8 / 16.8ms |
| 영상 가속 디코딩 비활성 | 16.8 / 16.8ms |

요청을 막으면 사라졌지만 첫 데이터 수신 뒤 재생만 멈추면 남았다. 첫 로드와 디코더 준비를 살펴볼 근거가 생겼다. VP9은 두 실행의 편차가 컸고 VP8은 둘 다 16.8ms였다. 가속 비활성 플래그는 원인을 좁히는 데만 사용했다.

720×450 타깃의 draw를 건너뛴 실행에서도 83.3/66.7ms가 남았다. 이 크기를 굴절과 bloom 일부가 함께 사용하므로 굴절만 분리한 실험으로 취급하지 않았다.

### RAF·JS·GPU가 재는 범위

기존 H.264 두 실행에서 JS RAF 콜백 최댓값은 3.9/2.8ms, 유효한 WebGL GPU 쿼리 최댓값은 약 6.95/6.49ms였다. RAF 간격에는 콜백 밖의 스케줄링, 네이티브 미디어 처리, 합성 대기도 들어간다. WebGL 쿼리는 영상 디코더와 합성기의 전체 작업을 포함하지 않는다.

CDP Media 기록에서 H.264 모니터는 `D3D11VideoDecoder`, VP8은 `VpxVideoDecoder`를 사용했다. 가속을 끈 H.264와 작은 조명 영상은 `FFmpegVideoDecoder`였다.

추가 trace에서 GPU 자원 준비와 디코드 span은 각각 약 31ms였고 대부분 겹쳤다. 첫 영상 데이터·프레임과 긴 RAF의 시점이 겹치는 데까지 확인했으며, 각 네이티브 단계의 기여율은 구하지 못했다.

## VP8 적용 후의 첫 진입

두 영상을 기존과 같은 640×400·24fps·10초의 VP8로 재인코딩했다. 첫 진입 때 WebM 지원 여부로 형식을 고르고, 미지원이면 기존 MP4를 사용한다. 재생 실패 시에는 절차적 영상으로 돌아간다. 화질과 형식 선택은 [영상 모니터 글](04-monitors.md)에 남겼다.

| 측정 | 기존 | 최종 |
| --- | --- | --- |
| 첫 진입 7초 | 2회 최대 99.9 / 83.3ms | 독립 3회 모두 최대 16.8ms |
| 전체 하강 19초 | 2회 최대 66.6 / 83.3ms | 2회 모두 최대 16.8ms |
| 전체 상승 19초 | 2회 모두 최대 16.8ms | 2회 모두 최대 16.8ms |

최종 첫 진입 3회의 RAF 간격은 총 1260개였다. 33.5ms 초과는 없었고 측정한 스크롤 구간의 품질 계수는 1.00이었다. 같은 구간에서 longtask·컴파일·링크·브라우저 오류는 0이었다. 최종 코드에는 아래 가시성 수정도 포함된다. 코덱만 분리한 비교는 앞의 조건별 표다.

![실험별 최대 프레임 간격](../images/frame-evidence.png)

*실측 기록을 다시 그린 차트. 위아래 패널은 빌드·구간·반복 횟수가 다른 실험이며 가로축 범위도 다르다.*

## 경계 뒤에서도 실행되던 굴절·반사

모니터와 리액터가 겹치면 주 화면 외에 굴절 배경과 수면 반사를 그린다. 전환 경계가 완전히 닫힌 뒤에도 이 패스가 실행되고 있었다.

| 변경 전 | 변경 후 |
| --- | --- |
| ![가시성 최적화 전의 65% 장면](../../screenshots/performance/before/scroll-650.jpg) | ![가시성 최적화 후의 65% 장면](../../screenshots/performance/after/scroll-650.jpg) |

*실제 화면. 1440×900, DPR 1, 스크롤 65%, 기본 시점·포인터 입력 없음. 논리 시계 270프레임과 영상 2초로 위상을 맞춘 화질 비교다.*

완전히 닫힌 경계에서는 그룹을 숨겼다. 일부가 열린 경우 판과 테두리를 화면에 투영해 굴절 캡처가 필요한지 판단했다. 첫 등장·재진입·타깃 재준비 때는 바로 캡처해서 이전 배경이 남지 않게 했다.

주 카메라 밖의 모니터가 수면 반사에는 보일 수 있었다. 따라서 물체 전체를 숨기는 대신 각 패스의 카메라로 캡처 여부를 판단했다. 수면에서는 다음 코드를 사용한다.

```ts
surface.onBeforeRender = function (...args) {
  visibility.begin(args[2])
  if (!visibility.intersects(surface, upper, lower)) return
  reflect.apply(this, args)
}
```

근접면에 걸쳐 투영 결과가 불확실할 때는 계속 그린다. 테스트에는 주 카메라 밖의 물체, 간접 반사, 절두체 재진입, 다른 카메라에서 보이는 수면을 넣었다. 이 부분은 Aether에 추가한 최적화와 회귀 검사 기록이다.

## draw 감소와 GPU 시간

요청 스크롤 59~69%에서 draw가 있는 RAF 콜백을 모아 두 반복을 합쳤다. GPU 값은 같은 콜백에 대응하는 유효한 쿼리만 사용했다.

| 방향 | 렌더당 평균 draw 전→후 | CPU p95 전→후 | GPU p95 전→후 |
| --- | ---: | ---: | ---: |
| 하강 | 152.71 → 133.83 | 3.8 → 3.9ms | 7.31 → 7.96ms |
| 상승 | 165.45 → 142.55 | 3.5 → 3.7ms | 6.46 → 5.71ms |

전체 렌더의 평균 GL 호출은 약 4% 줄었지만, 겹침 구간의 최대 217 draw는 남았다. GPU p95도 하강에서는 올라갔다. 동시에 보이는 모니터·리액터·수면을 계속 그려야 했고, 호출 감소가 곧 GPU 시간 감소로 이어지지는 않았다.

뒤이은 PR #16의 챔버 보강에서는 하강 최대 draw가 217→226으로 늘었다. 해당 왕복의 RAF 최대는 전후 16.8ms, GPU p95는 하강 4.35→3.92ms·상승 4.41→4.68ms였다. 각 수치는 그 빌드의 표본으로 보관했다.

측정 로그에는 요청 스크롤과 보간된 렌더 진행률을 함께 남겼다. 화면 telemetry는 15렌더마다 갱신되어 전체 프레임 집계에는 쓰지 않았다. 이 글의 16.8ms도 해당 데스크톱에서 얻은 관측값이다. 실제 Safari/iOS, 저사양 기기, 장시간 발열·메모리 검사는 남아 있다.
