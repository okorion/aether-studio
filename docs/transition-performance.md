# 스크롤 전환 멈춤 분석과 수정

PR #10의 첫 스크롤 멈춤 기록이다. 당시 남은 모니터 진입 지연은 [PR #15 분석](monitor-transition-performance.md)에서 다시 조사했다. 아래 수치는 이 문서의 전후 빌드에만 해당한다.

2026-09-22, 전환 구간을 처음 통과할 때만 길게 멈추는 문제를 재현했다. 같은 페이지를 역방향으로 통과할 때는 최장 간격이 16.8ms였지만, 첫 하강에서는 본 컬럼 진입 649.9ms, 리액터 진입 2799.9ms, 하단 포레스트 진입 816.5ms가 기록됐다. 최초 사용 때 몰리는 셰이더·GPU 자원 준비가 핵심 원인이었다.

수정 후 같은 환경에서 최초 하강의 최장 프레임 간격은 **66.6ms**, 역방향은 **16.8ms**였다. 최초 모니터 진입에서 남은 한 프레임은 후속 분석 대상으로 남겼다. 모든 멈춤이 사라졌다거나 모든 기기에서 일정 FPS를 보장한다고 해석하지 않는다.

## 재현 조건과 증거

- 수정 전 기준: `af57c87`. 수정 후 성능 구현: `da14095`.
- Chromium / ANGLE D3D11, 1440 × 900, DPR 1, 로컬 프로덕션 빌드.
- 준비 상태 확인 후 1초 대기. 한 페이지에서 19초 동안 0→99% 하강, 800ms 대기 후 19초 동안 99→0% 상승.
- 매 `requestAnimationFrame`에서 스크롤을 진행하고 콜백 사이 간격·실제 렌더 진행률·draw 호출·자동 품질 값을 수집했다. 자연스러운 휠 입력 검수와 구분되는 통제된 연속 스크롤 측정이다.
- `PerformanceObserver`의 `longtask`와 WebGL 함수 래퍼를 함께 사용했다. `compileShader`, `linkProgram`은 모두 기록하고, 나머지 감시한 GL 호출은 JavaScript에서 관측한 호출 시간이 2ms를 넘을 때 기록했다.

공개 증거 파일: [수정 전 요약·장시간 프레임·셰이더 링크](performance/before.json), [수정 후 같은 형식의 증거](performance/after.json). 각 파일에는 원본 보고서 경로와 SHA-256, 10개 스크롤 구간 통계, 기준 커밋을 포함한다. 로컬 원본은 `.qa/transitions-v10/{baseline,primed}/report.json`이다.

희소한 긴 멈춤은 전체 p95에 드러나지 않았다. 따라서 중앙값이나 평균 FPS만 비교하지 않고 최장 간격·장시간 프레임 수·전환 중 셰이더 생성 여부를 함께 판단했다. 첫 콜백의 불완전한 간격은 전체 통계에서 제외했다.

| 첫 하강의 전환 | 수정 전 최장 간격 | 수정 후 대응 구간 최장 간격 |

구간 표는 측정 스크립트가 요청한 스크롤 위치로 묶었다. 긴 프레임이 끝날 때 요청 위치는 앞으로 뛰지만 화면의 보간된 위치는 뒤에 남을 수 있다. 예를 들어 리액터 진입의 2799.9ms 프레임은 요청 진행률 약 75.5%, 기록된 렌더 진행률 약 59.8%다. JSON에 두 값을 모두 보존했다.

## 변경한 준비 흐름

**광원 구성을 고정했다.** 리액터 광원이 숨겨지는 그룹 아래에 있으면 리액터 등장 시 렌더러가 보는 광원 개수가 바뀐다. 이때 해당 광원 개수에 의존하는 여러 머테리얼의 셰이더 변형이 새로 필요했다. 광원은 장면에 계속 두고 강도만 리액터 노출량에 따라 바꾸도록 수정했다. 원래 리액터의 밝기·색·등장 시점은 유지한다.

**첫 화면 준비 중 숨겨진 장면도 컴파일한다.** bloom·굴절의 선형 half-float 출력과 직접 캔버스에 그리는 출력은 같은 머테리얼에서도 프로그램 변형이 다를 수 있다. 두 경로에 `compileAsync`를 적용해 스크롤 중 처음 생성되는 프로그램을 준비 단계로 옮겼다. Three.js는 장면의 조명과 환경을 구성한 뒤 사전 컴파일하도록 안내하며, 비동기 버전은 병렬 셰이더 컴파일 확장을 사용한다. [Three.js WebGLRenderer 공식 문서](https://threejs.org/docs/pages/WebGLRenderer.html)

**실제 첫 사용도 2 × 2 렌더 타깃에서 준비한다.** 컴파일만 완료해도 첫 uniform 조회나 지오메트리 업로드가 남을 수 있다. CSS 대체 화면이 보이는 동안 작은 타깃에 한 번 그려 이 작업까지 먼저 수행한다. 이 과정에서 임시 변경한 visibility·frustum culling·렌더 콜백·기존 타깃은 복구하고 임시 타깃은 해제한다. 컨텍스트 손실이나 해제 중 취소된 준비가 이후 장면을 깨우지 않도록 수명도 관리한다.

**정적 텍스처와 렌더 타깃을 미리 업로드한다.** wrapper 캔버스와 정적 재질 맵은 `initTexture`, 모니터 굴절·바닥 반사 타깃은 `initRenderTarget`으로 준비한다. 영상은 이 과정에서 다운로드·재생하지 않아 기존 지연 로드 동작을 유지한다. `initTexture`는 첫 렌더 시 디코드·GPU 업로드로 생길 수 있는 지연을 줄이는 데 쓰인다. [Three.js 텍스처 초기화](https://threejs.org/docs/pages/WebGLRenderer.html#initTexture)

**모니터 캡처 안의 바닥 재반사를 막았다.** 리액터와 모니터가 겹치는 동안 모니터 굴절용 배경 캡처가 바닥 반사를 다시 실행하던 경로를 제거했다. 캡처 중만 바닥 반사를 숨기고 이후 복구하므로 본 화면의 바닥 반사는 유지한다. 겹침 구간의 중복 패스를 줄이는 변경이며, 파티클 수나 화면 해상도를 낮추는 방식으로 이번 결과를 얻지 않았다.

## 비용과 남은 한계

수정 후 측정 스크립트가 `ready`를 확인한 시각은 탐색 시작 기준 **3675.9ms**였다. 수정 전 원본에는 동일한 초기 준비 시각이 없으므로 초기 로딩이 빨라졌다거나 몇 ms 느려졌다고 비교할 수 없다. 준비 작업을 첫 전환에서 초기 표시 전으로 이동한 만큼, 초기 준비 시간도 이후 지속해서 측정해야 한다.

위 수치는 **RAF 콜백 간격**이며 GPU 타이머 쿼리 결과가 아니다. 함수 래퍼 자체의 비용이 포함되고, 호출이 반환된 뒤 GPU에서 일어나는 작업이나 브라우저 합성기·영상 디코더의 전체 비용을 분리하지 못한다. 첫 모니터 진입의 66.6ms 구간에서는 longtask와 기록 조건에 걸린 GL 호출이 없었지만, 이것만으로 원인을 영상 또는 GPU라고 단정할 수 없다.

두 측정의 콘솔 오류는 0건이었다. 이번 자료는 한 데스크톱 환경에서의 비교이며 실제 Safari/iOS, 저사양 GPU, 고해상도 DPR 환경의 결과를 대신하지 않는다. 자동화 회귀·운영 접속 검증은 릴리스 검증 결과와 함께 확인한다. 우선순위는 [후속 개선 제안](next-improvements.md)에 정리했다.
