# Three.js 스크롤 카메라의 좌표계와 드래그 처리

AETHER는 링을 지나 본 컬럼, 리액터, 스케일 패널, 마지막 숲으로 내려가는 3D 페이지다. 처음에는 스크롤해도 내려가는 느낌이 약했다. 중앙의 모델만 다른 모양으로 바뀌는 것 같았다. 드래그로 옆면을 보다가 손을 놓으면 카메라도 다시 정면으로 돌아왔다.

이 글에서는 카메라 경로와 입력 처리를 수정한 과정을 정리했다. ‘본 컬럼’은 관절 모양의 금속 모델을 부르는 이름이다. Three.js의 `Bone`으로 만든 리깅 모델은 아니다.

## 링에서 벌어지는 리본

링에 붙인 리본은 정면에서는 맞아 보였다. 그런데 링을 기울이면 연결부가 벌어졌다. 두 오브젝트를 서로 다른 그룹에 넣고 따로 회전시키고 있었다.

```ts
// 수정 전 구조를 줄인 예시
world.add(emblem)
world.add(ribbons)

emblem.rotation.y = pointerTilt
ribbons.rotation.y = anotherMotion
```

리본의 회전값을 비슷하게 맞춰도 중심이 다르면 연결점은 어긋난다. 리본을 링의 부모 그룹인 `emblem` 아래로 옮겼다.

```ts
emblem.add(ribbons)
```

연결점을 링의 로컬 좌표로 지정하고 리본의 독립 회전도 지웠다. 이후에는 링에 위치·회전·크기 변환을 적용하면 리본에도 그대로 전달됐다.

![링·리본의 부모 좌표계](../images/coordinates.png)

*구조도. 오른쪽은 링과 리본이 하나의 부모 변환을 받는 구성이다.*

## 원점에 머물던 카메라

기존 카메라 경로에는 거리와 수평·수직 각도만 있었다. 카메라는 계속 같은 원점을 보고 있었고, 주변 공간도 중심 모델을 따라 움직였다. 이 구성으로는 아래층에 들어가는 모습을 만들기 어려웠다.

경로에 중심의 높이 `journey.height`를 추가했다. 카메라와 시선의 중심은 함께 내려가되, 리액터와 스케일 패널은 정해진 층에 남겨 뒀다.

```ts
// 카메라 위치 계산을 줄인 예시
focus.set(0, journey.height, 0)
camera.position.copy(focus).add(orbitOffset)
camera.lookAt(focus)
```

리액터 중심은 `Y=-40.4`, 바닥은 `Y=-44.1`, 스케일 패널은 `Y=-48`에 배치했다. 상위 그룹이 내려가므로, 고정할 물체의 로컬 높이에는 상위 그룹의 이동량을 빼 줬다. 그 결과 월드 좌표는 그대로 유지된다.

```ts
root.position.y = journey.height
space.position.y = chamberHeight - journey.height
scaleWall.position.y = scaleHeight - journey.height
```

마지막 전환도 같은 식으로 바꿨다. 스케일 패널을 줄여서 링으로 바꾸던 연출을 없애고, 카메라가 패널 아래로 내려가도록 했다.

![수정한 카메라의 하강 동작](../../screenshots/motion/entry-wheel.gif)

*당시 휠 입력 캡처를 묶은 GIF. 재질은 초기 버전이며 GIF 재생 간격은 앱의 FPS와 무관하다.*

경로는 24개 기준점을 사용한다. 구간마다 `smoothstep`을 따로 적용하면 기준점을 지날 때마다 속도가 0으로 줄어든다. 같은 방향의 이동이 이어지도록 인접 구간의 기울기를 고려한 cubic 보간을 적용했다. 수평 회전값도 한 바퀴마다 잘라 내지 않고 누적 각도로 저장했다.

## 손을 놓으면 정면으로 돌아가는 현상

드래그를 끝낼 때 목표 각도를 0으로 초기화하고 있었다.

```ts
// 수정 전
const release = () => {
  held = false
  targetYaw = 0
  targetPitch = 0
}
```

해제 시 각도 초기화를 제거했다. 드래그 중에는 시작 각도에 이동량을 더하고, 손을 놓은 뒤에는 남은 각속도를 서서히 줄인다.

```ts
// 회전 관성 처리
if (orbitEnabled && !held) {
  targetYaw += velocityYaw * delta
  velocityYaw *= Math.exp(-7 * delta)
}
```

수평으로는 여러 바퀴 돌 수 있게 하고 수직 각도는 제한했다. 마우스를 누를 때마다 실행되던 줌은 제거했다. 기본 시점으로 돌아가는 입력은 빈 공간 더블클릭으로 옮겼다.

옆면에서 포인터 흔적이 어긋나는 문제도 있었다. 흔적을 고정된 `z=0` 평면에 놓으면 옆으로 돌아간 시선과 평면이 거의 평행해진다. 포인터 광선이 만나는 평면을 현재 중심을 지나고 카메라를 향하는 방향으로 바꿨다.

## 중간 장면의 회전 잠금

본·모니터·리액터·스케일 구간은 큰 회전을 잠근다. 그런데 전환 중 금속 구조가 아직 보이는 시점에 드래그가 풀렸다. 입력 허용 조건과 카메라에 회전을 적용하는 가중치가 서로 달랐다.

두 곳 모두 `orbitWeight`를 사용하도록 맞췄다. 잠금에 들어갈 때 진행 중인 드래그와 각속도도 비운다. 잠긴 동안 쌓인 입력이 다음 장면에서 한꺼번에 적용되는 것을 막기 위해서다.

![회전 잠금 수정 전](../../screenshots/mechanical-lock/before-drag-result.jpg)
![회전 잠금 수정 후](../../screenshots/mechanical-lock/after-drag-result.jpg)

*1440×900, 스크롤 90%에서 같은 700px 수평 드래그를 적용한 화면. 영상·조명 시각은 고정하지 않았다.*

잠금 해제 구간은 이후 스케일 퇴장에 맞춰 94~97.5%로 조정했다. 카메라가 잠겨도 모니터 선택과 입자 반응은 받는다.

세로 드래그가 반대로 동작하던 부분은 y축 부호를 수정했다. 화면 좌표는 아래쪽이 양수이고 NDC는 위쪽이 양수다. 수평 회전과 잠금 조건은 유지한 채 수직 입력만 바꿨다.

## 정지와 복귀 확인

스크롤을 멈췄는데 본과 체인이 계속 흐르는 문제는 위치 계산에 섞인 재생 시간을 제거해 해결했다. 구조의 위치를 절대 스크롤 값으로 계산하면 같은 위치로 돌아왔을 때 같은 모양이 나온다. 영상과 조명에는 재생 시간을 계속 사용한다.

모션 설정을 바꾸면서 장면을 다시 만들 때는 yaw·pitch·경과 시간을 ref로 넘겼다. 중지 중 더블클릭으로 시점이 바뀌지 않는지도 확인했다. 마지막 링에 적용되던 Z축 180도 회전은 제거하고 리본의 방향만 따로 처리했다.

휠로 왕복하며 월드 높이를 읽고, 같은 스크롤 값에서 본·체인의 인스턴스 행렬을 비교했다. 드래그 해제·취소·창 포커스 이탈·모션 재개 후의 시점도 검사했다. 이 수정 뒤에도 첫 모니터 진입의 긴 프레임은 남았다. 그 문제는 [성능 분석 글](05-performance.md)에서 다룬다.
