# 파티클을 늘려도 자연스럽지 않았던 이유

본 컬럼 주변에 체인과 입자는 있었다. 하지만 체인은 옆에 매달린 장식처럼 보였고, 마우스 흔적은 가시처럼 늘어났다. 리액터에서는 포인터 주변에 너무 또렷한 원형 빈 공간이 생겼다.

문제를 입자 개수로 해결하기는 어려웠다. 어디를 따라 움직이는지, 무엇이 움직임을 시작하는지, 입력이 끝난 뒤 어디로 돌아가는지가 먼저 정해져야 했다.

이번 글은 체인 경로와 입자 반응을 수정한 기록이다. 화면 표현을 바꾼 작업과 실제 입력 오류를 함께 다루되 구분해서 적었다.

## 앞에 하나, 뒤에 하나 놓아도 감긴 체인은 아니다

체인이 본 컬럼을 감으려면 **각 체인 자체가** 앞과 뒤를 지나야 한다. 체인 하나를 앞에, 다른 하나를 뒤에 놓는 배치만으로는 부족했다.

경로를 두 줄의 나선으로 바꿨다. 한 바퀴의 각도에 따라 x와 z를 함께 바꾸고, y를 따라 올라가면서 여러 번 회전하게 만든다.

```ts
// 개념을 줄인 예시: 높이 t를 따라 본 컬럼 앞뒤를 도는 경로
const angle = t * Math.PI * 2 * turns + strandOffset

position.set(
  Math.cos(angle) * radius,
  (t - 0.5) * height,
  Math.sin(angle) * radius,
)
```

실제 구현은 두 체인이 각각 약 2.15회전하며, 본 컬럼의 굴곡과 반지름 변화도 반영한다. 타원 링크의 긴 방향은 같은 경로의 접선에 맞췄다. 다음 링크는 90도 방향을 교차해 연결된 형태로 보이게 했다.

![이전 본 컬럼과 체인](../../screenshots/living/before-340.jpg)

![나선 경로로 수정한 본 컬럼과 체인](../../screenshots/living/after-340.jpg)

*같은 1440×900, 34% 스크롤 위치의 당시 실제 화면이다. 앞뒤 감김과 모델 구성을 비교하는 사진이며 정지·역방향 동작 자체를 증명하는 자료는 아니다. 영상과 반짝임의 시각도 고정하지 않았다.*

검사는 체인 전체의 평균 위치로 끝내지 않았다. 각 체인이 본 컬럼의 앞뒤 z범위를 모두 통과하는지, x/z의 네 방향에 위치하는지, 높이순으로 따라갔을 때 누적 회전이 한 바퀴를 넘는지 확인했다. 두 체인을 앞뒤에 나란히 세운 구현이라면 이 검사를 통과할 수 없다.

## 움직임을 시간에 연결할지 스크롤에 연결할지

체인 경로가 맞아도 재생 시간으로 계속 흘려보내면 스크롤을 멈췄을 때도 움직인다. 같은 지점에 돌아왔을 때 처음 위치와 달라지는 문제도 생긴다.

구조와 체인은 절대 스크롤 위치로 계산한다.

```ts
// 실제 체인 경로에 쓰는 위상 계산
const t = THREE.MathUtils.euclideanModulo(
  i / linksPerStrand + progress * 3.4,
  1,
)
```

현재 위치에서 `delta`를 계속 더하는 방식이 아니다. `progress`가 같으면 `t`도 같다. 루프가 처음으로 돌아가는 끝부분은 크기를 줄여 갑자기 나타나지 않도록 했다.

같은 progress로 120번 갱신했을 때 본 컬럼·체인의 행렬이 동일한지, 다른 위치로 이동했다가 돌아오면 복원되는지 검사했다. 정지 상태에서는 인스턴스 행렬 업로드도 생략한다. 이 모델은 절차적 geometry와 `InstancedMesh`로 구성하며, 물리 체인이나 스킨드 메시 리깅은 사용하지 않는다.

주변 입자에도 두 가지 역할을 줬다. 흐름을 따라 이동하는 입자와 상대적으로 조용히 남아 있는 입자다.

```glsl
// 실제 shader에서 사용하는 역할 분리
float phaseScroll = motionTime() * aAdvected;
```

`aAdvected`가 0이면 스크롤 위상에 따른 이류를 하지 않는다. 1이면 흐름을 따라 이동한다. 여기서 고정은 화면에 붙어 있다는 의미가 아니다. 카메라가 내려가면 입자도 다른 위치에 보인다.

본 컬럼에서 포인터 근처의 추가 이동은 현재 스크롤 변화량과 같은 방향으로 적용했다. 스크롤이 멈추면 이 추가 위치 변화도 멈춘다. 반면 영상과 미세한 빛 변화에는 시간을 계속 사용한다.

![입자 역할, 공유 흐름 격자와 전진하는 잔광의 관계](../images/particle-flow.png)

*설명용 도식. 본 컬럼의 스크롤 이동, 포레스트의 포인터 흐름, 포인터 스트릭의 재생 시간은 서로 다른 입력이다.*

## 정지한 리액터는 마우스에 반응하지 않았다

본 컬럼 입자가 리액터로 내려가 O를 이루는 흐름은 유지해야 했다. 하지만 이 입자 이동에 사용하던 ‘스크롤 변화량이 있을 때만’이라는 조건이 리액터 반응에도 남아 있었다.

그래서 스크롤을 멈추면 마우스를 움직여도 입자의 위치가 바뀌지 않았다. 조명만 변하는 것으로는 요구한 반응이 나오지 않았다.

본 컬럼의 스크롤 변위와 리액터의 포인터 변위를 분리했다. 리액터 구간에서는 스크롤이 0이어도 포인터 가까이 있는 입자를 움직인다. 보이는 입자와 커서의 거리는 투영된 화면 좌표에서 계산하고, 위치 변형은 view 공간에서 적용한다. 뒤쪽 깊이와 화면비가 달라도 커서 주변의 보이는 O가 반응하도록 한 것이다.

이후에는 반응이 너무 명확한 문제가 생겼다. 입자가 일정한 원주로 밀려나며 가운데가 뻥 빈 원처럼 보였다.

![이전 리액터의 원형 포인터 영향 범위](../../screenshots/pointer/before/720-move.jpg)

![영향 범위를 완화한 리액터](../../screenshots/pointer/after/720-move.jpg)

*72% 위치에서 같은 포인터 경로를 사용한 전후 화면이다. 조명 프레임 차이가 있으므로 빈 공간과 O의 폭을 비교하는 자료로 사용했다. 위치 변형 여부는 별도 픽셀 검사로 확인했다.*

고정 반경을 기준으로 영향력을 자르던 처리를 넓은 Gaussian 감쇠로 바꿨다. 포인터 중심에서도 무조건 바깥 방향으로 강하게 정규화해 밀지 않도록 했고, 입자마다 영향 폭과 접선·깊이 반응을 조금씩 다르게 줬다.

모든 입자를 같은 원주로 보내는 대신, 가까운 영역이 느슨하게 휘어지게 만드는 조정이었다. 입력이 사라지면 원래 O를 만드는 계산으로 돌아간다.

이 과정에서 중복된 코어도 정리했다. 연속 입자 흐름 외에 별도로 만든 본 컬럼·리액터 입자가 겹쳐 있었다. 일부는 진입 경계 위로 새기도 했다. 중복 코어를 제거하고 같은 입자 흐름이 O로 수렴하게 했다. 원래 씨드와 리액터의 월드 높이는 유지했다.

## 포레스트가 움직이지 않는 배경처럼 보였다

초기 포레스트의 둥근 입자 군집은 가지가 이어진 공간보다 구체 덩어리에 가까웠다. 이것은 기능 장애보다는 목표한 공간 표현과의 차이였다.

절차적으로 만든 줄기·가지·고사리형 잎과 미세 입자로 바꾸고, 상단과 하단 포레스트를 월드 공간에 고정했다. 이제 링을 중심으로 카메라를 돌리면 앞쪽 가지와 뒤쪽 가지의 이동량, 서로 가리는 순서가 달라진다.

포레스트를 링과 똑같이 회전시키는 방식은 아니다. 같은 공간 안에서 카메라가 돌기 때문에 함께 반응하는 것처럼 보인다. 실제로 카메라 각도를 바꾸기 전후의 가지 월드 행렬은 같고, 화면에 투영된 위치는 깊이에 따라 다르게 변하는지 검사했다.

카메라 가까이 온 가지가 화면 전체를 덮는 문제는 깊이에 따른 fade로 완화했다. 중앙 링 주위에는 열린 공간을 남겼다. 이후에는 기존 입자 예산의 일부를 높은 가지와 잎에 재배치해 하단 포레스트로 진입할 때 상부 수관이 먼저 보이도록 했다.

## 포인터의 현재 위치만 저장하면 이전 흐름이 사라진다

포레스트에는 포인터의 위치에서 잠깐 밝아지는 효과 외에, 입자가 이동 방향을 따라 느리게 끌리는 반응이 필요했다. 포인터가 지나간 두 곳에 서로 반대 방향의 움직임이 남을 수도 있어야 했다.

화면 전체에 작은 **40×28 흐름 격자**를 두었다. 포인터 이동 방향을 주변 셀에 기록하고, 시간이 지나면 약하게 퍼지고 감쇠한다. 입자는 이 격자를 읽어 지연된 움직임을 따라간다.

입자마다 CPU에서 위치를 반복 계산하지 않는다. 공유 텍스처 하나를 읽는다. RGBA8 텍스처 자체는 4,480바이트이며, 별도의 draw나 장면 캡처는 추가하지 않았다. CPU에는 격자 계산용 고정 배열이 있다.

하단 포레스트나 드래그된 카메라에서도 화면 방향이 뒤집히지 않도록, 격자의 방향을 카메라의 오른쪽·위쪽 축으로 변환한다. 줄기와 뿌리는 고정하고 잎은 낮은 세기로, 미세 입자는 실제 정점 위치로 반응한다.

전환 경계에서 반응이 달라 보인다고 입력을 끄지는 않았다. 보이는 포레스트에는 같은 흐름을 적용한 뒤 기존 사선 경계로 가렸다. 다른 장면에 숨겨진 입자가 효과 때문에 다시 새어나오지 않게 순서를 유지했다.

첫 접촉이나 긴 입력 공백 뒤에는 위치만 기록한다. 이전 커서 위치와 갑자기 연결하면 화면을 가로지르는 가짜 흐름이 생길 수 있기 때문이다. UI·터치·취소·탭 숨김·화면 이탈에서는 흐름을 비운다. 이 부분은 입력 수명을 안전하게 만들기 위한 보강이다.

## 가시처럼 늘어나던 잔광은 선두가 실제로 움직이지 않았다

포인터 스트릭을 길고 부드럽게 바꾸는 것만으로는 원하는 동작이 나오지 않았다. 생성점에서 길이만 늘어나면 끝이 뾰족한 가시처럼 읽혔다.

수정 후에는 선두 광점이 시간에 따라 곡선을 따라 전진한다. 잔광의 각 정점은 같은 경로의 조금 더 과거 위치를 읽는다.

```glsl
// 개념을 줄인 예시
vec2 head = flight(age);
vec2 tail = flight(max(0.0, age - delay));
```

실제 구현에는 스트릭마다 다른 완만한 굽힘, 폭, 밝기를 넣었다. 선두와 잔광이 같은 함수를 읽으므로 서로 벌어지지 않는다. 카메라 하강 때문에 굵기가 갑자기 변하지 않도록 폭은 화면 픽셀 기준으로 환산했다.

검사에서는 입력을 멈춘 뒤에도 선두의 실제 픽셀이 전진하는지 확인했다. 1.6초 뒤에는 잔광이 남고, 3초 뒤에는 모두 사라지는지도 확인했다. 수명은 2.35초로 제한했다.

## 색이 바뀐 것과 위치가 바뀐 것은 다르게 검사했다

입자가 반짝이면 마우스에 반응한 것처럼 보일 수 있다. 그래서 위치 검사는 조명 영향을 줄인 고정 시계에서 alpha coverage, 즉 입자가 실제로 차지하는 픽셀 영역을 비교했다.

리액터는 스크롤 변화량이 0이어도 영역이 달라지고, 입력 강도가 0이 되면 원래 픽셀로 돌아와야 했다. 포레스트는 양 끝과 전환 경계에서 같은 방향으로 움직이고 복귀해야 했다. 체인은 행렬로 정지와 역방향을 검사했다.

화려함을 숫자로 인증한 작업은 아니다. 특히 정착 후 한 장비에서 얻은 프레임 간격을 모든 기기의 성능으로 확대할 수 없다. 이번 수정에서 확인한 것은 감김, 정지, 복귀, 입력 방향처럼 다시 검사할 수 있는 동작이다.
